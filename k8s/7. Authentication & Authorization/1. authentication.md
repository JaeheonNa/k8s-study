### 일반적인 TLS 통신 흐름

              [client]                                                    [server]
    1.                             -----------요청----------->   
    2.                             <---public key & CA crt---
    3. 안전한 Server인지 CA crt 확인
    4. public key로 대칭키 암호화
    5.                             --------암호화된 대칭키------->
    6.                                                             private key로 암호화된 대칭키 복호화
    7.                         (서로 공유 중인 대칭키로 데이터 암복호화 통신)


### kubernetes API Authentication - 0
- master node에서는 별다른 조치 없이 cli로 kubectl을 통해 kubernetes API 접근이 가능함.
- kubectl이 생성될 때, kubernetes API 접근에 필요한 **Client key**와 **Client crt**를 갖고 생성되기 때문.


### kubernetes API Authentication - 1 (x509 client cert)
- client가 server의 신원을 확인하는 것처럼, server도 client의 신원을 확인해야 함.
- k8s server는 내부적으로 **Client key**와 **Client crt**, **CA key**, **CA crt**를 갖고 있음.
-  k8s cluster 외부에서 kubernetes API Server에 접근하려면 server가 갖고 있는 **Client key**와 **Client crt**가 필요함.
- (**CA crt**는 자신이 안전한 서버임을 client에게 알려주기 위한 인증서임.)
- (client가 **Client key**와 **Client crt**로 server에 요청을 하면, server는 자신이 갖고 있는 CA key와  **CA crt**, **Client key**로 **Client crt**를 만들어 client가 보낸 **Client crt**가 유효한지 확인함.)
- kubectl도 생성될 때 **Client key**와 **Client crt**를 갖고 생성됨. 그래서 kubectl을 통해 kubernetes API에 접근이 가능한 것임.
- **Client key**와 **Client crt**, **CA crt**는 Master Node의 아래 경로에서 확인할 수 있음.

> cat /etc/kubernetes/admin.conf

- 단, base64로 인코딩된 상태이므로, 아래와 같이 디코딩이 필요함.

> grep 'client-certificate-data' /etc/kubernetes/admin.conf | head -n 1 | awk '{private $2}' | base64 -d \
> grep 'client-key-data' /etc/kubernetes/admin.conf | head -n 1 | awk '{private $2}' | base64 -d 

- 위에서 디코딩한 내용을 각각 파일로 만든 후 아래와 같은 방법으로 접근 가능. (아래 요청은 node 정보를 리스트업하는 API 요청)
> curl -k --key ./[admin.key] --cert ./[admin.cert] https://[k8s cluster IP]:6443/api/v1/nodes


### kubernetes API Authentication - 2 (kubectl proxy)
- 만약 kubectl에 accept-hosts 옵션으로 8001번 포트에 Proxy를 띄워두면, k8s cluster 외부에서 **Client key**와 **Client crt** 없이 kubectl proxy를 통해 kubernetes API 접근이 가능해짐.
> nohup kubectl proxy --port=8001 --address=[k8s cluster IP] --accept-hosts='^*$' >/dev/null 2>&1 &


### kubernetes API Authentication - 3 (Service Account)
- kubectl 자체를 k8s cluster 외부에 설치하여 kubectl에 접근함으로써 kubernetes API에 접근하는 방법도 있음.
- 외부의 kubectl은 context switching을 통해 여러 cluster에 요청을 날릴 수 있음.


                         |-->  cluster-a --> kubernetes API
    client --> kubectl --| 
                         |-->  cluster-b --> kubernetes API


- 대신 이 경우의 kubectl은 k8s cluster에 대한 정보와 user 정보를 묶은 context가 필요함.
> kubectl 설치 방법 url: https://kubernetes.io/docs/tasks/tools/install-kubectl-macos/

    apiVersion: v1
    clusters:
    - cluster:
      name: cluster-a
        certificate-authority-data: [CA crt]
        server: https://[k8s cluster-a IP]:6443
    - cluster:
      name: cluster-b
        certificate-authority-data: [CA crt]
        server: https://[k8s cluster-b IP]:6443
    contexts:
    - context:
      name: context-a
        cluster: cluster-a
        user: admin-a
    - context:
      name: context-b
        cluster: cluster-b
        user: admin-b
    current-context: context-a
    kind: Config
    preferences: {}
    users:
    - name: admin-a
      user:
        client-certificate-data: [Client crt]
        client-key-data: [Client key]
    - name: admin-b
      user:
        client-certificate-data: [Client crt]
        client-key-data: [Client key]

- 아래 명령어로 context를 변경할 수 있음. 즉, cluster를 변경하여 접근할 수 있음.
> kubectl config use-context [context명]

### kubernetes API Authentication - 4
- Service Account가 사용하는 token을 이용하는 방법도 있음.
- namespace를 생성하면 기본적으로 Service Account도 default로 생성되는데, 이 Service Account는 **CA crt**정보와 token이 담긴 Secret을 사용함. 
- (Pod를 해당 namespace에 생성하면, Pod는 default Service Account에 연결되어 token값으로 kubernetes API에 접근 가능하게 됨.)
- token만 있으면 외부에서도 kubernetes API 접근 가능함.

> Secret명 확인: kubectl describe -n [namespace명] [ServiceAccount명] \
> token 확인: kubectl describe -n [namespace명] [Secret명]

- 위에서 확인한 token을 header의 Authentication 속성에 'bearer [token]'을 넣어 요청하면 됨.
