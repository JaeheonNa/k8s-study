### Ingress
- 요청하는 url에 따라 각각의 Service를 타도록 LoadBalancing을 해주는 object.


    www.hl-chat.com/users                     |-->  /users      --> Service1 --> Pod(user)
    www.hl-chat.com/rooms       --> Ingress --|-->  /rooms      --> Service2 --> Pod(rooms)
    www.hl-chat.com/messages                  |-->  /messages   --> Service3 --> Pod(messages)

- Ingress object 자체는 껍데기이고, NginX와 같은 구현체, 즉 Ingress Controller가 필요함.
- Ingress에 구현해야할 내용을 적어두면, Ingress Controller가 설치될 때, Ingress를 확인하여 구현함.


    apiVersion: networking.k8s.io/v1beta1
    kind: Ingress
    metadata:
        name: service-loadbalancing
    spec:
        rules:
        - http:
            paths:
                - path: /user
                  backend:
                    serviceName: Service1
                    servicePort: 8080
                - path: /rooms
                  backend:
                    serviceName: Service2
                    servicePort: 8080
                - path: /messages
                  backend:
                    serviceName: Service3
                    servicePort: 8080

- 위 예제의 경우 Ingress에 Host는 [www.hl-chat.com]으로, Path는 ['/users', '/rooms', '/messages']로, ServiceName은 각각 ['Service1', 'Service2', 'Service3']로 정의해두면,
- Ingress Controller가 설치될 때, Namespace, Deployment, ReplicaSet, Pod를 순차적으로 생성되고, Pod안에 Ingress Container를 띄워 구현함.
- 모든 요청은 Ingress Container가 구현된 Pod를 거쳐야하므로,  해당 Pod를 물고 있는 Service(NodePort든 LoadBalancer든)를 만들어야 함. (k8s 1.27부터는 NodePort도 NginX Ingress Controller와 함께 설치됨.)

> NginX Ingress Controller 설치 command \
> kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.8.2/deploy/static/provider/baremetal/deploy.yaml

- Canary 배포 시 Ingress를 활용할 수도 있음. 새 버전의 Pod를 띄우고, 새 Ingress를 추가하면 됨. 이 때 몇 %의 트래픽을 새 버전의 Pod(Canary Pod)로 돌릴지 weight를 주는 게 핵심


    apiVersion: networking.k8s.io/v1
    kind: Ingress
    metadata:
      name: canary-v2
      annotations:
        nginx.ingress.kubernetes.io/canary: "true"
        nginx.ingress.kubernetes.io/canary-weight: "10"
    spec:
      ingressClassName: nginx
      rules:
      - host: www.app.com
        http:
          paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: svc-v2
                port:
                  number: 8080

- 지역 별로 Canary 배포할 땐 header 옵션을 사용할 수 있음.
- 아래 예제는 client의 요청 header에 Accept-Language 속성과 그 값으로 kr이 담겨 왔을 때, canary Pod로 요청이 가도록 하는 예제임.


    apiVersion: networking.k8s.io/v1
    kind: Ingress
    metadata:
      name: canary-kr
      annotations:
        nginx.ingress.kubernetes.io/canary: "true"
        nginx.ingress.kubernetes.io/canary-by-header: "Accept-Language"
        nginx.ingress.kubernetes.io/canary-by-header-value: "kr"
    spec:
      ingressClassName: nginx
      rules:
      - host: www.app.com
        http:
          paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: svc-v2
                port:
                  number: 8080


- https 요청만 받아들이도록 Ingress를 설정할 수도 있음. 물론 미리 secret을 만들어놔야 함.

> 인증서 생성 \ 
> openssl req -x509 -nodes -days 365 -newkey rsa:2048 -keyout tls.key -out tls.crt -subj "/CN=www.https.com/O=www.https.com"

> Secret 생성 \
> kubectl create secret tls secret-https --key tls.key --cert tls.crt

    apiVersion: networking.k8s.io/v1
    kind: Ingress
    metadata:
      name: https
    spec:
      ingressClassName: nginx
      tls:
      - hosts:
        - www.https.com
        secretName: secret-https
      rules:
        - host: www.https.com
          http:
            paths:
            - path: /
              pathType: Prefix
              backend:
                service:
                  name: svc-https
                  port:
                    number: 8080
